# 设计与实现说明

> 目标设备：OPPO Watch 46mm（型号 `OW20W1`）
> 版本：v0.1 · 2026-11-11

---

## 1. 目标与约束

### 1.1 用户目标
在 eSIM 安卓手表上，用**语音**与 AI 对话。界面尽可能简洁，安装包尽可能小。

### 1.2 硬件实测约束

| 项目 | 实测值 | 对设计的影响 |
|---|---|---|
| 系统 | Android 8.1.0 / **API 27** | `minSdk=21`、`targetSdk=27`，避开 API 28+ 的明文流量、后台限制 |
| 架构 | **armeabi-v7a（仅 32 位）** | 不能带任何 64 位 native 库；纯 Java 最安全 |
| 内存 | 1GB（可用约 475MB） | 不能用大型框架，不能常驻后台 |
| 存储 | /data 剩 1.9G | 安装包要小；音频只写 `cacheDir` 并复用 |
| 屏幕 | 402×476 px，密度被手动改成 200 | 布局按 **322dp × 381dp** 设计 |
| Google 服务 | **无 GMS** | 不能用 `SpeechRecognizer`、不能用 Firebase、不能用 Play 服务定位 |
| TTS | 无任何系统 TTS 引擎 | 只做文字显示，不做朗读 |
| WebView | 61.0.3163.98（2018） | 放弃网页方案（现代前端框架在 Chrome 61 上会语法报错） |
| 语音输入 | 搜狗手表输入法（有云端语音） | 可作为备用路径，但本应用自己录音更干脆 |

### 1.3 由此推导出的三条硬性设计原则

1. **零第三方依赖**：不引 AndroidX / Material / OkHttp / Gson。
   网络用系统 `HttpURLConnection`，JSON 用系统 `org.json`。
   这样就不需要 desugaring、不需要 ProGuard 规则、APK 能压到 200KB 以内。
2. **单 Activity 为主**：手表上多页面跳转成本高，主流程全部在一个 Activity 内完成。
3. **不做后台常驻**：没有 Service、没有通知、没有推送。用完即退。

## 3. 主流程（一次完整对话）

```
① 用户按住圆键
       │
       ├─ 检查 Config.ready()？没有 → 状态行提示「请先点右上角 ⚙ 填写 API Key」，返回
       ├─ 检查 RECORD_AUDIO 权限？没有 → requestPermissions()，返回
       │
       ▼
② MediaRecorder 开始录音
   格式：MPEG_4 容器 / AAC 编码 / 16kHz / 单声道 / 32kbps
   写入：getCacheDir()/q.m4a（复用同一个文件，每次先删）
   按钮变红，文字变「松开发送」
       │
       ▼
③ 用户松手
   recorder.stop() + release()
   文件 < 1200 字节 → 视为误触，「太短了，再按一次」
       │
       ▼
④ 后台线程：Api.transcribe()
   POST multippart → 硅基流动
   返回 { "text": "今天天气怎么样" }
   ← 失败：状态行显示「识别失败：xxx」
       │
       ▼
⑤ 主线程：addBubble("me", text)，history 追加 {user, text}
   同时**预建一个空的 AI 气泡**，记录为 lastAiBubble
       │
       ▼
⑥ 后台线程：Api.chat()
   POST → DeepSeek，stream=true
   逐行读 SSE，每拿到一个 token 就 ui.post 往 lastAiBubble 追加
   同时自动滚到底部
       │
       ▼
⑦ 流结束（[DONE]）→ history 追加 {assistant, 完整文本}，状态行恢复「按住说话」
```

### 3.1 为什么「预建空气泡」

流式输出时如果每来一个 token 就新建一个 TextView，会产生大量 View，在 1GB 内存的手表上会造成 GC 卡顿。预建一个 TextView 再不断 `setText()`，全程只增加一个 View。

### 3.2 为什么用 `StringBuilder` 而不是直接读 TextView

`target.getText()` 在每次回调都要做一次字符串拷贝，累加复杂度 O(n²)。用 `StringBuilder` 累加，最后一次 `setText(acc.toString())` 是 O(n)。

### 3.3 线程模型

| 线程 | 做什么 |
|---|---|
| 主线程 (UI) | 所有 View 操作、MediaRecorder 的 start/stop |
| Thread-A | `Api.transcribe()` —— 一次性的短请求 |
| Thread-B | `Api.chat()` —— 长连接流式读取 |
| `ui` Handler | 把 Thread-A/B 的结果 post 回主线程 |

**规则**：`Api` 类里的回调 `TokenCallback` 在**后台线程**触发，调用方负责 `ui.post`。这条规则写死在代码里，不要在 `Api` 内部做线程切换。

### 3.4 上下文控制

只发送最近 **8 条**消息（`trimmedHistory()`），配合 `max_tokens=512`。
原因：DeepSeek 按 token 计费，手表场景多是短问短答，保留长历史既贵又没必要。

System prompt 固定为（`Api.SYSTEM_PROMPT`，静态常量）：

> 你在手表上回答。极简：能一句话说清就不说第二句，准确优先于客套。不用 Markdown、不用列表、不解释过程、不复述问题。中文。

三个约束都有明确的理由：

- **不用 Markdown**：手表上渲染不了 `**粗体**`，星号会原样显示出来
- **不解释过程、不复述问题**：这两件事在手机上占两三行无所谓，在 402px 宽的表盘上会直接把回答挤出屏幕
- **静态常量**：DeepSeek 命中 prompt cache 时输入按 $0.003/M 计费（cache miss 是 $0.15/M），
  这 40 个字几乎不产生成本

### 3.5 会话生命周期

```
启动应用
   │
   ├─ SessionStore.beginNewSession()
   │     session_current.json  ──rename──▶  session_last.json
   │     （旧的 last 被覆盖，等于"之前的全部删掉"）
   │
   └─ history 清空（本来就是内存态）→ 界面显示一句引导语

每产生一条消息
   │
   └─ SessionStore.append(role, text)  ──▶ session_current.json
```

**关键点：存档不参与上下文。**
`session_last.json` 只是留个记录，下次启动时不会被读回、不会拼进请求。
AI 看到的永远只有本次会话的消息。

磁盘占用上限：两个 JSON 文件，每个通常几 KB。

## 4. 外部接口

### 4.1 语音识别 — 硅基流动 SenseVoiceSmall

```
POST https://api.siliconflow.cn/v1/audio/transcriptions
Authorization: Bearer <ASR_KEY>
Content-Type: multipart/form-data; boundary=----watchai<timestamp>

--boundary
Content-Disposition: form-data; name="model"

FunAudioLLM/SenseVoiceSmall
--boundary
Content-Disposition: form-data; name="file"; filename="a.m4a"
Content-Type: audio/mp4

<二进制音频>
--boundary--
```

响应：

```json
{ "text": "今天天气怎么样" }
```

- **价格：免费**（2026-11 官方定价页标注「免费」，按 UTF-8 千字符计费但价格为零）
- 限制：单文件 50MB / 1 小时、有 RPM 限流、2026-05-15 起需实名认证
- 隐私：音频会经过第三方，敏感内容不要用

### 4.2 对话 — DeepSeek

```
POST https://api.deepseek.com/chat/completions
Authorization: Bearer <DS_KEY>
Content-Type: application/json
```

```json
{
  "model": "deepseek-chat",
  "stream": true,
  "max_tokens": 512,
  "messages": [
    { "role": "system", "content": "你是一个手表上的语音助手……" },
    { "role": "user",   "content": "今天天气怎么样" }
  ]
}
```

响应是 SSE，每行形如：

```
data: {"choices":[{"delta":{"content":"今"}}]}
data: {"choices":[{"delta":{"content":"天"}}]}
data: [DONE]
```

`Api.chat()` 的解析规则：
- 只处理以 `data:` 开头的行
- `[DONE]` 表示结束
- 单行 JSON 解析失败**不中断**对话（`catch (Exception ignore)`），防止某个畸形分片打断整段输出

### 4.2.1 语音识别方案对比（2026-11 官方价格）

前提：一轮手表对话（5 秒语音）的 DeepSeek 成本约 ¥0.0015～0.003。
**语音成本必须低于这个数**，否则不如直接打字。

| 方案 | 计费方式 | 5 秒一次 | 占 AI 成本 | 免费额度 |
|---|---|---|---|---|
| **硅基流动 SenseVoiceSmall** | 每千字符（UTF-8），当前标价「免费」 | **¥0** | **0%** | 无限，仅 RPM 限流 |
| 火山 豆包录音文件识别 2.0 | 0.8 元/小时 | ¥0.0011 | 37%～73% | 20 小时（半年） |
| 火山 豆包一句话识别 | 3.5 元/千次，量大降至 1 元/千次 | ¥0.0035 | 117%～233% ❌ | 20 小时（半年） |
| 讯飞 语音听写 | 1300 元 / 50 万次 | ¥0.0026 | 87%～173% | 每天 500 次 + 5 万次包（90 天） |

**结论：只有硅基流动免费档能达标。**
若要换供应商，选火山的「录音文件识别」而不是「一句话识别」——后者按次计费，比问一次 DeepSeek 还贵。

**换供应商的代码成本**：`Config` 已暴露 `asr_url` / `asr_model`，但 `Api.transcribe()`
按 OpenAI 兼容格式解析 `{"text": "..."}`。火山 / 讯飞的响应结构不同，需要改解析逻辑，不是改配置就行。

### 4.3 成本模型

DeepSeek `deepseek-flash` 官方价（2026-11）：

| | 谷时 | 峰时 |
|---|---|---|
| 输入（cache miss） | $0.15 / 1M | $0.30 / 1M |
| 输出 | $0.60 / 1M | $1.20 / 1M |

一轮对话按 600 输入 + 200 输出 token 估算：**≈ ¥0.0015（谷时）/ ¥0.003（峰时）**。
语音识别 ¥0，占 AI 成本 0%。

峰时段：UTC 01:00–04:00 与 06:00–10:00（周一到周五，中国法定节假日除外）。

## 5. UI 设计

### 5.1 尺寸推导

```
屏幕 402×476 px，密度 200 dpi
dp = px × 160 / 200 = px × 0.8
宽 402px → 321.6dp
高 476px → 380.8dp
```

### 5.2 布局分配（垂直）

| 区域 | 高度 | 内容 |
|---|---|---|
| 顶栏 | wrap | 左「AI」标签 + 右齿轮 ⚙ |
| 对话区 | `weight=1`（吃掉剩余空间） | ScrollView，隐藏滚动条 |
| 状态行 | wrap，11sp | 「按住说话」/「正在听…」/「识别中…」/「思考中…」 |
| 按钮区 | 120dp | 居中圆形按钮 |

按钮 120dp 在 321dp 宽里占 37%，拇指能够到且不挡内容。

### 5.3 配色

| 用途 | 色值 |
|---|---|
| 背景 | `#0B0B0F` |
| AI 气泡 | `#1C1C22` |
| 用户气泡 | `#1E88E5` |
| 正文 | `#EDEDED` / `#FFFFFF` |
| 次要文字 | `#808090` |
| 录音中按钮 | `#D32F2F` |

深色为主是 AMOLED 手表上的必然选择——省电，且 402×476 的屏在户外强光下对比度更高。

### 5.4 气泡规则

- 用户消息靠右，AI 消息靠左
- 气泡宽度 `weight=0.86`，留出 14% 给「这是谁说的」的视觉暗示
- 圆角 12dp，内边距 10dp×7dp
- 每条消息外面包一个 `row`（`LinearLayout`），靠 `gravity` 决定贴左贴右

### 5.5 交互

| 操作 | 结果 |
|---|---|
| 按住圆键 | 开始录音，按钮变红显示「松开发送」 |
| 松手 | 结束录音并发送 |
| 按住后滑出/被系统打断（`ACTION_CANCEL`） | 取消录音，不发送 |
| 点右上角 ⚙ | 进设置 |

## 6. 配置存储

`SharedPreferences`，文件名 `watchai`。

| key | 默认值 |
|---|---|
| `deepseek_key` | 空 |
| `asr_key` | 空 → 自动复用 `deepseek_key`（`Config.effAsrKey()`） |
| `deepseek_url` | `https://api.deepseek.com` |
| `deepseek_model` | `deepseek-chat` |
| `asr_url` | `https://api.siliconflow.cn/v1` |
| `asr_model` | `FunAudioLLM/SenseVoiceSmall` |

URL 和模型都留了覆盖入口，方便以后换供应商（比如把 `asr_url` 指向火山引擎，`deepseek_url` 指向任何 OpenAI 兼容端点）。

**在手表上手工输入长 Key 很痛苦**。安装后可以直接用 adb 写入：

```bash
adb shell run-as com.yao.watchai \
  sh -c 'mkdir -p shared_prefs && cat > shared_prefs/watchai.xml <<EOF
<?xml version="1.0" encoding="utf-8" standalone="yes" ?>
<map>
    <string name="deepseek_key">sk-xxxxxxxx</string>
</map>
EOF'
```

（要求 APK 是 debuggable 的；正式版走设置界面输入。）

## 8. 构建

不使用 Gradle，直接调 SDK 工具链，避免 Gradle 下载几百 MB 依赖：

```
aapt2 compile --dir app/res -o build/res.zip
      ↓
aapt2 link  --manifest … -R res.zip -I android.jar -o base.apk
      ↓
javac       -source 8 -target 8 -bootclasspath android.jar -d classes
      ↓
d8          --release --min-api 21 --output dex *.class
      ↓
zip         把 classes.dex 塞进 base.apk
      ↓
zipalign -f 4
      ↓
apksigner sign --ks debug.keystore
```

执行：`./build.sh`

首次运行会自动用 `keytool` 生成 `debug.keystore`（密码 `android`）。

### 8.1 为什么不用 Gradle
- Gradle + AGP 本身就要下载数百 MB
- 本项目无任何依赖、无 flavor、无 buildConfig 需求
- 直接调工具链，构建时间 < 5 秒，产物体积可控

### 8.3 国内网络下的工具链获取

`dl.google.com` 在国内会被限速（实测 148MB 的 commandlinetools 卡在 73MB 后完全停住）。
用腾讯云镜像 `https://mirrors.cloud.tencent.com/AndroidSDK/` 直取同名文件，速度约 7MB/s：

| 文件 | 放到 |
|---|---|
| `commandlinetools-mac_arm64-15859902_latest.zip` | `sdk/cmdline-tools/latest/`（解压后目录名改为 `latest`） |
| `build-tools_r34-macosx.zip` | `sdk/build-tools/34.0.0/`（解压出的 `android-14` 改名） |
| `platform-27_r03.zip` | `sdk/platforms/android-27/`（解压出的 `android-8.1.0` 改名） |
| `emulator-darwin_aarch64-16863232.zip` | `sdk/emulator/` |
| `sys-img/android/arm64-v8a-27_r02.zip` | `sdk/system-images/android-27/default/arm64-v8a/` |

注意 `build-tools_r34-macosx.zip` 是 universal binary（含 arm64），
Apple Silicon 上原生运行，不需要 Rosetta。

### 8.2 体积控制
- 无第三方依赖 → 无需要 ProGuard 删的东西
- 资源只有 `strings.xml` + 一个 XML 形状图标
- 无 native 库
- 预期 APK **< 200KB**

## 9. 运行与调试

### 9.1 模拟器（当前不可用）

`run-sim.sh` 会创建 402×476 / 密度 200 / API 27 的 AVD，但**实测起不来**：

- API 27 的 `arm64-v8a` 镜像在 emulator 37.3.9 上，surfaceflinger 能起来，但客户机时钟
  在开机约 2 分钟处停止推进，`/data/dalvik-cache` 创建失败，`system_server` 始终未启动
- 已排除：`-wipe-data` / `-partition-size 2048` / `-gpu swiftshader_indirect` / `-no-audio`
- 结论：调 UI 靠真机截图（`adb exec-out screencap -p` + `uiautomator dump` 量边界）

如果以后要重试，最可能有效的是换更高 API 的镜像（如 `system-images;android-30;default;arm64-v8a`），
但那样就失去了"系统版本与手表完全一致"的价值。

### 9.2 真机（手表）

```bash
adb install -r watchai.apk
adb shell monkey -p com.yao.watchai -c android.intent.category.LAUNCHER 1
```

前提：
1. 手表 设置 → 其他设置 → 关于手表 → 连点版本号 7 次 开启开发者模式
2. 打开 USB 调试
3. 放磁吸底座，底座接电脑
4. 设备上点「允许 USB 调试」

### 9.3 密度
手表当前被设为 `wm density 200`（出厂 320）。

```bash
adb shell wm density 200    # 当前
adb shell wm density 320    # 出厂
adb shell wm density reset  # 清除覆盖
```

**注意**：320 下系统 UI 是正常比例，但抖音/QQ/网易云这类手机 App 会变得巨大难用；200 是折中值。

## 10. 已知限制

| 限制 | 原因 | 可能的解法 |
|---|---|---|
| 没有语音朗读 | 系统无 TTS 引擎，云端 TTS 要额外费用 | 接硅基流动 CosyVoice（按字符计费） |
| 无离线能力 | 无本地 ASR/LLM，1GB 内存跑不动 | 不现实 |
| 免费 ASR 有 RPM 限流 | 硅基流动免费档 | 并发高时切火山引擎（20 小时试用） |
| 音频经过第三方 | 免费档的代价 | 敏感内容手动打字 |
| 手表上输入 Key 很痛苦 | 无实体键盘 | 用 adb run-as 写 prefs |
| 不保存历史 | 未做持久化，退出即清空 | 可加 Room / 简单文件存储 |

## 11. 扩展点

按优先级：

1. **TTS 朗读**：在 `Api.chat()` 的 `onDone()` 里把完整文本发给 TTS 接口，播放音频文件
